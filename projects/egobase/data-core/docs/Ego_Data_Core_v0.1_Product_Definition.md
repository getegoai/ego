# Ego Data Core v0.1 产品定义

**版本**：v0.1 内部执行稿  
**日期**：2026-05-28  
**项目代号**：Ego / ShadowNode  
**文档性质**：产品定义 + MVP 边界 + 技术架构 + 90 天执行计划  
**核心目标**：定义 Ego 从“硬件智能体终端”进入“个人数据操作系统”的第一阶段产品形态。

---

## 0. 一句话定义

**Ego Data Core 是一个本地优先、24 小时运行的个人数据操作系统。它保存用户原始数据，持续生成增强数据，分层调度本地 PC、本地服务器、Ego 节点和外部算力，并通过物理级电脑操作能力，把用户数据转化为主动行动。**

更短的产品表达：

> **Ego Data Core：你的本地数据大脑与硬件智能体。**

内部工程表达：

> **Ego Data Core = Original Evidence Vault + Enhanced Data Twin + Active Work Graph + Compute Scheduler + Physical Operator。**

---

## 1. 背景判断

### 1.1 AI 产品交互范式正在变化

当前主流 AI 产品仍以“用户提问—模型即时回答”为核心。但这种模式不适合作为个人长期智能体的最终形态。

真正的个人智能体不应只是等待用户提问，而应当：

1. 持续观察用户数据变化；
2. 持续整理用户资料；
3. 发现待办、风险、冲突和机会；
4. 在低风险场景下主动执行；
5. 在高风险场景下向用户汇报并请求授权；
6. 随着用户数据积累越来越了解用户。

因此，Ego Data Core 的产品范式不是 Chatbot，而是：

> **异步、后台、持续运行的个人数据智能体。**

---

### 1.2 “智能体记忆压缩”不是 Ego 的核心路线

市场上已经出现大量智能体记忆、上下文压缩、长期记忆管理产品。这类产品通常将对话、文档、行为记录处理为摘要、向量、偏好、图谱或 key-value memory。

这些技术有工程价值，但存在根本问题：

> **如果压缩后的摘要、向量或图谱替代了原始数据，记忆就不可逆地降精度了。未来模型再强，也只能在被压缩过的数据上推理。**

Ego Data Core 不采用“压缩数据替代记忆”的路线，而采用：

> **原始数据完整保留，增强数据持续生成，运行时上下文临时组装。**

这意味着：

- 原始数据是真相；
- 增强数据是解释；
- 上下文只是临时工作视图；
- 模型输出不能覆盖原始证据；
- 未来模型升级后，可以基于原始数据重新生成更高质量增强数据。

---

### 1.3 Ego 的差异点不是“会记住”，而是“能保存、增强、行动”

Ego Data Core 与普通记忆产品、知识库、网盘、NAS、RAG 系统的区别：

| 类别 | 核心能力 | 局限 |
|---|---|---|
| 网盘 | 存文件 | 不理解、不主动、不行动 |
| NAS | 本地存储 | 偏设备和文件，不是智能体 |
| RAG 知识库 | 检索资料 | 以问答为中心，缺少长期主动工作 |
| Agent Memory | 存偏好和摘要 | 容易用压缩记忆替代原始数据 |
| API 网关 | 路由模型调用 | 不掌握用户原始数据和物理执行权 |
| Ego Data Core | 保存原始数据、生成增强数据、建立工作图谱、主动汇报、物理执行 | 第一阶段需要控制采集范围，避免过宽 |

Ego 的核心不是“记忆层”，而是：

> **个人数据资产的持续采集、证据保存、增强整理和主动执行系统。**

## 2. 产品定位

### 2.1 总定位

**Ego Data Core 是 Ego 的第一阶段核心产品能力，用于将用户 PC、本地文件、屏幕事件、操作记录和后续感知数据转化为可追溯、可增强、可行动的个人数据资产。**

它是 Ego 的“数据底座”，也是未来 Ego Operator、Ego Home、Ego Work、Ego Sense Kit 和 Ego Compute Fabric 的基础。

---

### 2.2 面向用户的定位

> **Ego Data Core 会在你工作时持续整理你的文件、屏幕、项目和任务，并每天向你汇报：你做了什么、产生了哪些资料、哪些事情没有完成、哪些问题值得关注、哪些工作可以由 Ego 自动完成。**

---

### 2.3 面向投资人的定位

> **Ego Data Core 是本地优先的个人数据操作系统。它以硬件智能体为入口，保存用户原始数据，持续生成增强数据，分层调度算力，并把个人长期上下文转化为可执行的主动任务。**

---

### 2.4 面向技术团队的定位

> **Ego Data Core 是一个 evidence-first data pipeline：以原始证据库为中心，通过异步增强流水线生成结构化数据孪生，再由任务图谱、模型调度和物理操作模块驱动主动执行。**

---

## 3. 产品边界

### 3.1 v0.1 做什么

v0.1 只做 PC 工作流中的个人数据管理和主动汇报，不做全场景泛化。

v0.1 必须完成：

1. 本地文件索引与原始证据库；
2. 指定目录的文件变化监控；
3. 屏幕关键状态采集；
4. 活跃窗口与应用使用记录；
5. 文件、截图、网页快照的增强数据生成；
6. 项目归类与资料关联；
7. 待办、风险、冲突、问题自动发现；
8. 每日主动汇报 Ego Daily Brief；
9. 低风险自动化建议；
10. 与 Ego Operator 的接口预留。

---

### 3.2 v0.1 不做什么

v0.1 明确不做：

1. 不做全量手机数据接管；
2. 不做微信、QQ、企业微信等复杂 IM 的深度解析；
3. 不做全天候全量录屏；
4. 不做全天候全量录音；
5. 不做家庭儿童安全正式产品；
6. 不做企业级多人权限系统；
7. 不做公网分布式算力市场；
8. 不做专用芯片；
9. 不做模型训练平台；
10. 不做通用 AI 问答产品。

---

### 3.3 v0.1 的核心约束

v0.1 必须满足：

1. **Local-first**：核心数据默认本地保存；
2. **Evidence-first**：增强数据必须可追溯原始证据；
3. **Non-destructive**：模型生成内容不得覆盖原始数据；
4. **Asynchronous-first**：优先支持后台异步处理，而不是即时聊天；
5. **Human-authorized**：高风险动作必须由用户授权；
6. **Model-agnostic**：不能绑定单一模型；
7. **Compute-adaptive**：可调度 PC、本地服务器、Ego 节点和外部模型；
8. **Operator-ready**：为后续物理级电脑操作预留接口。

## 4. 核心用户与首发场景

### 4.1 首批用户画像

v0.1 不面向大众家庭用户，而面向高价值早期用户：

| 用户类型 | 痛点 | Ego 价值 |
|---|---|---|
| 一人公司创业者 | 文件、客户、项目、合同、资料混乱 | 自动整理项目资料，发现待办，生成日报 |
| 开发者/AI 创作者 | 项目资料多、代码和文档分散 | 项目上下文整理、自动生成问题清单 |
| 教师/科研人员 | 课件、资料、论文、学生作业分散 | 资料归类、教案素材整理、任务提醒 |
| 内容创作者 | 素材、脚本、发布计划混乱 | 素材管理、选题追踪、发布建议 |
| 小型团队负责人 | 多项目并行、信息分散 | 每日项目状态汇报和风险发现 |
| 高级自动化爱好者 | 想让 AI 真正替自己工作 | 本地数据底座 + 后续物理操作能力 |

---

### 4.2 首发场景

v0.1 聚焦三个首发场景：

#### 场景 A：个人项目资料自动整理

用户指定一个或多个工作目录，Ego 持续监控文件变化，自动生成：

- 项目列表；
- 文件归属建议；
- 新增资料摘要；
- 重复资料提醒；
- 重要文件标记；
- 项目时间线；
- 项目未决问题。

#### 场景 B：每日主动工作汇报

Ego 每天生成一份 Ego Daily Brief：

1. 昨天主要处理了哪些项目；
2. 新增了哪些重要文件；
3. 哪些文件可能属于同一项目；
4. 哪些事项出现中断；
5. 哪些承诺或待办需要跟进；
6. 哪些资料存在冲突或缺口；
7. 哪些工作 Ego 可以自动完成；
8. 哪些事项需要用户决策。

#### 场景 C：自动化机会发现

Ego 从用户操作记录和文件变化中发现重复流程，例如：

- 每天整理下载文件；
- 重复复制粘贴表格；
- 固定格式生成文档；
- 定期打开网页后台；
- 将会议记录整理成任务；
- 将多个文件合并成报告。

Ego 不立即执行高风险动作，而是先生成：

> **“我发现了一个可以自动化的流程，是否授权我下次自动完成？”**

## 5. 产品核心架构

Ego Data Core v0.1 由九个核心模块组成。

---

### 5.1 Ego Vault：原始证据库

**定位**：保存用户原始数据和可追溯证据。

保存对象：

1. 原始文件；
2. 文件版本；
3. 文件元数据；
4. 关键截图；
5. 活跃窗口记录；
6. 网页快照；
7. 操作事件；
8. 任务输入输出；
9. 模型调用记录；
10. 用户授权记录。

设计原则：

- 不用摘要替代原始文件；
- 不用向量替代原始内容；
- 不用图谱替代证据；
- 所有增强数据必须能追溯到 Ego Vault 中的证据；
- 原始数据默认本地保存；
- 重要数据支持加密存储；
- 用户可查看、导出、删除原始证据。

推荐存储结构：

```text
/ego_vault
  /sources
    /pc_files
    /screenshots
    /web_snapshots
    /events
    /operator_logs
  /objects
    /documents
    /images
    /videos
    /audio
    /code
  /versions
  /evidence_index
  /audit_logs
```

---

### 5.2 Ego Twin：增强数据孪生

**定位**：基于原始证据生成可计算、可检索、可重算的增强数据。

增强类型：

| 原始数据 | 增强数据 |
|---|---|
| 文档 | 摘要、主题、实体、关键段落、风险点、相关项目 |
| 截图 | OCR 文本、UI 元素、窗口结构、应用状态 |
| 网页 | 正文、标题、来源、可信度、主题标签、快照 |
| 代码 | 函数、模块、依赖、变更说明、潜在问题 |
| 图片 | 场景描述、文字识别、对象标签 |
| 操作日志 | 重复流程、常用软件、任务切换、自动化机会 |
| 项目目录 | 项目状态、资料缺口、时间线、下一步建议 |

重要原则：

- 增强数据不是事实本身；
- 增强数据可以多版本并存；
- 增强数据可以因模型升级而重算；
- 每条增强数据都记录生成模型、时间、置信度和证据来源；
- 用户确认后的增强数据要标记为 verified。

---

### 5.3 Ego Work Graph：主动工作图谱

**定位**：将文件、项目、人物、任务、时间和操作连接起来，形成用户的主动工作状态。

核心节点：

- Project；
- File；
- Person；
- Task；
- Event；
- Decision；
- Risk；
- Question；
- Automation Opportunity；
- Report。

核心关系：

- belongs_to；
- related_to；
- created_by；
- modified_at；
- mentioned_in；
- depends_on；
- blocks；
- needs_decision；
- can_be_automated；
- evidence_of。

示例：

```text
File: Ego投资人方案_v3.docx
  belongs_to -> Project: Ego融资材料
  related_to -> File: Ego_Data_Core_v0.1.md
  contains -> Task: 补充商业模式部分
  evidence_of -> Question: Ego到底是数据产品还是硬件产品？
```

---

### 5.4 Ego Night Shift：异步后台工作系统

**定位**：让 Ego 在用户不操作时持续整理数据。

任务类型：

1. 新文件入库；
2. 文档解析；
3. OCR；
4. 项目归类；
5. 重复文件检测；
6. 任务提取；
7. 风险识别；
8. 未决问题生成；
9. 周期性报告生成；
10. 自动化机会挖掘。

调度原则：

- 实时任务优先级低；
- 夜间处理大批量任务；
- 高耗能任务可延后；
- 高隐私任务只在本地处理；
- 可外部处理任务必须先脱敏；
- 所有处理结果写入 Ego Twin 和 Ego Work Graph。

---

### 5.5 Ego Brief：主动汇报系统

**定位**：将 Ego 的后台工作成果转化为用户可理解、可决策的简报。

v0.1 输出：

1. Daily Brief；
2. Weekly Brief；
3. Project Brief；
4. Data Health Brief；
5. Automation Brief。

Daily Brief 标准结构：

```text
Ego Daily Brief
日期：YYYY-MM-DD

1. 昨日主要项目
2. 新增重要资料
3. 文件归类建议
4. 未完成事项
5. 风险与冲突
6. 值得追问的问题
7. Ego 可自动完成的工作
8. 需要你授权的动作
9. 证据链接
```

简报要求：

- 每条结论必须能追溯证据；
- 不确定内容必须标注为推测；
- 不替用户做高风险决策；
- 不堆砌无价值信息；
- 以“下一步行动”为中心。

---

### 5.6 Ego Model Router：模型分层调度

**定位**：根据任务类型、隐私等级、模型能力、成本和时延，选择合适模型。

模型分层：

| 层级 | 模型类型 | 用途 |
|---|---|---|
| L0 | 规则与启发式算法 | 文件监控、事件触发、权限判断 |
| L1 | 小模型 1.5B–3B | 分类、标签、简单摘要、意图识别 |
| L2 | 本地 7B–14B | 文档整理、项目归类、日报草稿 |
| L3 | 本地服务器/GPU | 批量增强、复杂项目分析、代码处理 |
| L4 | 外部强模型 | 高难推理、复杂写作、战略分析 |
| L5 | 未来专用硬件模型 | 高频固定任务加速 |

基本策略：

- 敏感数据默认本地处理；
- 外部模型只接收最小必要上下文；
- 外部模型不能访问完整 Ego Vault；
- 外部模型不能直接执行动作；
- 每次模型调用都记录成本、时间、输入、输出和隐私等级；
- 模型可替换，上层数据架构不变。

---

### 5.7 Ego Compute Fabric：算力协同层

**定位**：统一调度 PC、本地服务器、Ego 节点、局域网设备和外部算力。

v0.1 支持：

1. 当前 PC；
2. Ego Node 本机；
3. 局域网本地服务器；
4. 用户已有 GPU 工作站；
5. 可选外部云端模型。

未来支持：

1. 多 Ego Node；
2. 家庭/办公室 Ego Mesh；
3. 学校/团队可信算力池；
4. 专用硬件加速模块；
5. 低电价/光伏时段任务调度。

调度维度：

- 隐私等级；
- 任务优先级；
- 时延要求；
- 模型能力；
- 成本；
- 能耗；
- 当前设备负载；
- 可验证性。

---

### 5.8 Ego Operator：物理级操作模块

**定位**：让 Ego 不仅能整理数据，还能像人一样操作电脑。

v0.1 不要求完整实现，但必须预留接口。

能力方向：

1. HDMI 采集屏幕；
2. OCR 与 UI 元素识别；
3. USB HID 模拟键盘鼠标；
4. 执行动作前生成计划；
5. 执行动作后截图核验；
6. 失败后重试或请求人工介入；
7. 所有动作写入审计日志。

Ego Operator 是 Ego 与普通数据产品最大的差异点。

普通产品只能管理数据。  
Ego 最终要能基于数据执行动作。

---

### 5.9 Ego Safety Kernel：安全与权限内核

**定位**：确保 Ego 的数据采集、增强、调度和执行可控、可审计、可撤销。

v0.1 安全要求：

1. 默认本地存储；
2. 用户明确授权采集目录；
3. 用户明确授权屏幕采集范围；
4. 敏感数据标记；
5. 模型调用日志；
6. 外部调用脱敏；
7. 高风险动作人工确认；
8. 可暂停、可关闭、可删除；
9. 数据导出；
10. 审计日志不可被模型自行修改。

高风险动作包括：

- 删除文件；
- 发送消息；
- 提交表单；
- 支付；
- 修改合同；
- 修改代码仓库主分支；
- 上传敏感资料；
- 对外发送邮件；
- 修改系统设置。

## 6. 数据架构

### 6.1 数据对象分类

v0.1 核心数据对象：

| 对象 | 说明 |
|---|---|
| Source | 数据来源，如文件夹、屏幕、网页、应用 |
| RawObject | 原始对象，如文件、截图、网页快照 |
| Evidence | 可引用证据，如文件版本、截图区域、日志片段 |
| Enhancement | 增强数据，如摘要、标签、实体、OCR |
| Project | 项目空间 |
| Task | 任务或待办 |
| Question | 需要用户思考/决策的问题 |
| Risk | 风险或冲突 |
| Automation | 自动化机会 |
| Report | Ego 生成的汇报 |
| Action | Ego 执行或建议的动作 |
| Audit | 审计记录 |

## 8. 用户体验设计

### 8.1 第一次启动流程

1. 用户连接 Ego Node 或安装 Ego Data Core；
2. 选择本地工作目录；
3. 设置隐私等级；
4. 选择是否启用屏幕状态采集；
5. 选择本地模型和外部模型策略；
6. Ego 扫描目录并建立第一版 Evidence Index；
7. Ego 生成第一份 Data Health Brief；
8. 用户确认项目归类建议；
9. Ego 开始 Night Shift 后台增强。

---

### 8.2 日常使用流程

用户正常工作，不需要刻意打开 Ego。

Ego 在后台：

1. 观察文件变化；
2. 记录关键屏幕状态；
3. 分析新增资料；
4. 更新项目状态；
5. 生成问题和待办；
6. 发现自动化机会；
7. 在约定时间生成简报。

用户每天只需要看：

> **Ego Daily Brief**

并对其中的建议进行：

- 忽略；
- 标记正确；
- 修改；
- 授权 Ego 执行；
- 要求 Ego 深入分析。

---

### 8.3 核心交互不是 Chat，而是 Brief + Action

Ego Data Core 的默认界面不应是聊天框，而应是：

1. 今日简报；
2. 项目状态；
3. 待办与问题；
4. 自动化机会；
5. 数据证据；
6. 授权执行按钮。

聊天可以作为辅助入口，但不是主入口。

## 10. 安全、隐私与信任机制

### 10.1 数据主权原则

1. 用户拥有原始数据；
2. 用户拥有增强数据；
3. 用户可以导出数据；
4. 用户可以删除数据；
5. 用户可以关闭采集；
6. 外部模型无权直接访问完整数据；
7. 外部模型无权直接执行动作；
8. Ego 的每次处理都应可审计。

---

### 10.2 隐私等级

| 等级 | 说明 | 默认处理策略 |
|---|---|---|
| Public | 可公开资料 | 可外部处理 |
| Private | 普通私人资料 | 默认本地，外部需确认 |
| Sensitive | 敏感资料 | 仅本地处理 |
| Critical | 密码、财务、身份、医疗等 | 禁止模型读取或需逐次授权 |

---

### 10.3 用户控制

用户必须能控制：

- 哪些目录被监控；
- 哪些应用被记录；
- 是否采集屏幕；
- 截图频率；
- 哪些模型可用；
- 哪些数据可以外部处理；
- 哪些动作允许自动执行；
- 哪些数据永久删除；
- 哪些增强数据标记为错误。

## 13. 关键风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 范围过宽 | 想同时接 PC、手机、传感器、企业系统 | v0.1 只做 PC 文件 + 屏幕 + 简报 |
| 数据过多 | 存储、隐私、处理压力过大 | 不做全量录屏，采用关键帧和事件驱动 |
| 增强错误 | AI 把错误摘要写入长期系统 | evidence-first，增强数据可驳回、可重算 |
| 用户无感 | 后台整理看不出价值 | 以 Daily Brief 和行动建议作为主交互 |
| 变成知识库 | 只有搜索和问答 | 必须做主动问题、待办、自动化机会 |
| 变成 API 网关 | 只做模型调度 | 数据资产和物理执行权才是核心 |
| 硬件太早 | 被芯片路线拖慢 | 先用现成 PC/服务器/Ego Node 验证闭环 |
| 隐私风险 | 采集太激进 | 明确授权、可暂停、可删除、敏感等级 |

## 16. 当前定稿结论

Ego Data Core v0.1 的产品核心不是“AI 问答”，不是“记忆压缩”，不是“API 路由”，也不是“本地大模型盒子”。

它的核心是：

> **本地保存原始数据，持续生成增强数据，主动发现问题和任务，并最终通过硬件智能体执行动作。**

Ego Data Core 要先证明一个最小闭环：

```text
用户正常工作
  ↓
Ego 采集文件与屏幕证据
  ↓
原始数据进入 Ego Vault
  ↓
后台生成 Ego Twin 增强数据
  ↓
形成 Ego Work Graph
  ↓
生成 Ego Daily Brief
  ↓
用户确认或授权
  ↓
Ego 执行低风险任务或进入 Operator 阶段
```

最终目标：

> **让 Ego 成为用户数字生活和数字工作的长期数据大脑，而不是又一个短期聊天工具。**
